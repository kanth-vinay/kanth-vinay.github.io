Self-hosted Moodle · AWS · Cloudflare
The goal

A self-hosted, self-owned course platform — student data, pricing, and the underlying software all stay under your control rather than a vendor's. It behaves like Khan Academy's care-first ethos and IXL's rigor, deliberately not a high-volume enrollment funnel, while staying sound enough to support a future DESE-type partnership without a rebuild. First real test: the Extreme Algebra pilot.

How to use this document

This is a living document, not a one-time build log. It's meant to stay accurate for as long as ActiveSTEM Online runs — when a component changes, this page should be updated to match, so it stays trustworthy as the map rather than becoming a record of how things used to work.

Work through the five weekends in order the first time. After that, use the sidebar as a reference: jump straight to the section that matches whatever you're touching.

Prerequisites (MacBook Pro)

Since you are building and managing this entirely yourself, your MacBook Pro is your command center. You don't need heavy software, but you do need the right tools installed before starting Weekend 1 to avoid frustration.

Required software (free)
1. A proper code editor: Visual Studio Code Don't use TextEdit for writing scripts — it injects hidden formatting characters that break Linux scripts. Download VS Code to keep a local copy of your backup scripts, HTML documentation, and Moodle CSS.
2. A dedicated password manager You will be creating an AWS root account, an AWS IAM account, a Cloudflare account, a Moodle admin account, and a database password. Do not reuse passwords. Use 1Password (paid) or Bitwarden (free).
3. An authenticator app for MFA AWS requires Multi-Factor Authentication. Use Google Authenticator or Authy on your phone, or 1Password's built-in authenticator if you already have it.
4. Terminal (already installed) You will occasionally need to run commands. Press Cmd + Space and type "Terminal." You'll paste commands here when interacting with AWS Systems Manager. No extra software needed.

"Uploading" Moodle — what an AMI really is

This is worth clearing up before anything else, because it's the misunderstanding that makes the rest of Weekend 1 feel harder than it is: you never install Moodle yourself, and you never upload any files to AWS to make it appear. There is no upload step anywhere in this process.

What an AMI actually is

An AMI (Amazon Machine Image) is a complete, frozen snapshot of a computer's hard drive — operating system, installed software, configuration files, all of it — saved as a template. Launching an EC2 instance "from" an AMI means AWS copies that entire snapshot onto a new virtual machine and boots it up. It's the same idea as restoring a phone from a backup.

The Bitnami Moodle AMI specifically is a snapshot that a company called Bitnami builds and maintains: a small Linux server with a web server, PHP, MySQL, and the Moodle files already wired together. The moment it finishes booting (2-3 minutes), Moodle is already running on it.

What's actually inside the one server

This answers the "is it a database connected to Moodle" question directly: yes, and here's exactly how the pieces sit next to each other on the single EC2 instance you launch in Weekend 1.

All four boxes above are one machine — Bitnami wires them together automatically.

Where a login, an answer, and a grade go

Walking one real action all the way through the stack above, start to finish:

1. Student opens learn.activestem.org and enters a passwordThe browser sends this over an encrypted connection to Cloudflare, which forwards it on to your EC2 instance.
2. The web server (Apache) receives itIt sees the request is for a PHP application and hands it to Moodle's code.
3. Moodle checks the password against MySQLMoodle's PHP code looks up that email in the mdl_user table and compares the bcrypt-hashed password — never stored as plain text.
4. The student's dashboard loads from MySQLEnrollment and permissions come from mdl_role_assignments and mdl_context; the active login itself is tracked in mdl_sessions.
5. Student answers a hint-based problemWritten straight into mdl_lesson_attempts — which page, what they answered, right or wrong.
6. The gradebook updates instantlyReads live from mdl_grade_grades — not a separate system, just a view over the same tables.
7. Once mastery is met, the certificate plugin firesIt generates a PDF, saves it into the moodledata folder (a file, not a database row), then emails it via SES.
8. That night, both halves get backed upThe nightly cron job copies the MySQL database and the moodledata folder to S3 — a login problem is almost always MySQL, a missing file is almost always moodledata.

Weekend 1 · AWS foundations 4–6 hrs

Goal: end this weekend with a running server that only you can access.

1. Create the AWS account

Go to aws.amazon.com and click Create an AWS account. Use a dedicated email for this — not your personal UMSL address — since this account will hold billing and access. You'll be asked for a credit card; this month's usage will cost a few dollars.

Once you're in the console, check the region selector in the top-right corner (a dropdown showing something like "N. Virginia"). Every step from here on happens inside whichever region is selected there — stay on a US region such as us-east-1 (N. Virginia) for the lowest cost, and don't switch it mid-project or your instance will seem to "disappear" the next time you look.

2. Lock the root account with MFA

The account you just created is the "root" account — it can do anything, including delete everything.

Search IAM in the console's top search bar, find Add MFA for the root user, and set up two-factor authentication using your authenticator app (e.g. 1Password or Google Authenticator).

Do not skip this. A root account without MFA is the single biggest security hole in this entire setup.

3. Create a separate IAM admin user

You'll use this for daily work instead of the root login.

In IAM, click Users → Create user, name it something like vinay-admin, attach the AdministratorAccess policy, and enable MFA on this user too. From now on, log in as this user.

4. Launch the Bitnami Moodle instance

Read "Uploading" Moodle first — there is no upload step. This step boots a computer that already has Moodle.

This is the actual server that runs Moodle, start to finish.

a. Find the image: In the AWS Console, go to EC2 → Launch instance. Search Bitnami Moodle in "Application and OS Images" and switch to the AWS Marketplace AMIs tab.

b. Subscribe: The first time, AWS shows a subscription page — click Continue. It's free software; you only pay AWS for the compute and storage under it.

c. Name & size: Name it activestem-moodle-prod. Pick t3.small from the Instance Type list.

d. Create key pair: Click Create new key pair (RSA, .pem), name it, and download it to your MacBook. Save it somewhere safe — it can't be re-downloaded.

e. Network & storage: Leave the default VPC. Ensure storage is set to 30GB gp3 (gp3 is cheaper and faster than the default gp2).

f. Launch: Click Launch instance. Wait ~3 minutes for it to show "Running."

g. Confirm Moodle: Copy the Public IPv4 address from the instance details into your browser. You should see Bitnami's welcome page.

h. Get admin login: Default username is usually user. Default password is often the Instance ID (starts with i-) — but Bitnami has changed this between image versions before, so treat it as a starting guess. If it doesn't work, select the instance → Actions → Monitor and troubleshoot → Get system log, and search for "password."

5. Configure the security group (the locked door)

Allow only these three
443 (HTTPS)from anywhere (0.0.0.0/0) — normal web traffic
80 (HTTP)from anywhere (0.0.0.0/0) — needed briefly for SSL
22 (SSH)from My IP only — closed entirely in Weekend 2

6. Attach an Elastic IP

In the EC2 dashboard, go to Elastic IPs → Allocate, then associate it with your new instance. This gives your server a fixed address that won't change after a reboot.

7. Open a terminal on your server for the first time

Every step from here on that says "open a terminal" means what's on this page. You need this now because the swap file (next step) has to happen before Weekend 2 sets up the easier Session Manager method.

Exactly what to type, on your Mac

a. Open Terminal (Cmd + Space, type "Terminal"). Navigate to wherever you saved the .pem file from Step 4 — usually cd ~/Downloads.

b. Fix the file's permissions (AWS refuses to use it otherwise, one-time only): chmod 400 your-key-name.pem

c. Connect, replacing the key filename and IP with your own: ssh -i your-key-name.pem bitnami@YOUR_ELASTIC_IP

d. The first time, it will ask "Are you sure you want to continue connecting?" — type yes and press Enter. You're now looking at a Linux command prompt on your server, logged in as the bitnami user, which already has permission to touch Moodle's files directly — no extra sudo su step needed when connecting this way.

Once Weekend 2 sets up Session Manager, you'll mostly use that instead — it's the one that works without this key file, from anywhere. But Session Manager drops you in as a different user (ssm-user) that does not automatically have Moodle-file access — when using Session Manager, run sudo su - bitnami first to switch into the same context this SSH method gives you directly. Don't delete the .pem file either way; keep it as a fallback.
If you close your laptop and come back later from a different network (home vs. a coffee shop, for instance), this SSH connection will silently time out — the security group only allows the IP address you had when you set it up in Step 5. If that happens, go back to the security group, edit the port 22 rule, and select "My IP" again to refresh it to your current address. This stops being a problem entirely once Weekend 2 replaces this with Session Manager.
One command worth running the first time you connect, since almost everything from here on depends on it: ls /bitnami/moodle. You should see folders including moodledata and a file called config.php — if instead you get "No such file or directory," Bitnami's packaging has changed and the real path is likely /opt/bitnami/moodle instead; substitute that path everywhere this guide says /bitnami/moodle.

8. Create a memory safety net (swap file) critical

Because the t3.small instance has 2GB of RAM, a sudden spike in activity — several students submitting a quiz at once — can cause the server to run out of memory. When that happens, Linux forcibly kills something to cope, often MySQL, which crashes the site. A swap file borrows 2GB of your hard drive as emergency overflow memory, turning a crash into a brief slowdown.

In the terminal you just opened, run these one by one — you'll type them directly at the prompt you're already looking at:

sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

To make it survive a reboot, add it to fstab:

echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

Confirm it's active with free -h — the Swap row should show a non-zero number. This is a one-time setup, not something you'll touch again unless you resize the instance.

End of weekend 1 checkpoint: typing your instance's Elastic IP into a browser shows Bitnami's default Moodle welcome page, you can open a terminal via SSH, and free -h shows swap space is active.

Weekend 2 · Domain & access 4–6 hrs

Goal: end this weekend with learn.activestem.org loading securely, manageable from anywhere.

1. Add the domain to Cloudflare

Sign up at cloudflare.com (free plan) and add activestem.org. Cloudflare scans your DNS records and gives you two nameservers to update wherever the domain is registered.

This can take anywhere from a few minutes to 24–48 hours to fully take effect worldwide. If learn.activestem.org doesn't load right after finishing this weekend's steps, that's normal propagation delay, not a broken step — check back in a few hours before troubleshooting anything.

2. Point the subdomain at your server

In Cloudflare's DNS settings, add an A record: Name = learn, Value = your Elastic IP from Weekend 1. Make sure the proxy status (orange cloud) is on.

3. Turn on SSL

In Cloudflare's SSL/TLS settings, set the mode to Full. Do not choose "Full (Strict)" — Bitnami generates a self-signed certificate locally on the server, and Strict mode rejects certificates not issued by a recognized authority, which breaks the site.

If you later want Strict mode's extra guarantee, Bitnami includes a tool called bncert-tool that requests a real Let's Encrypt certificate for the server. A fine upgrade once things are stable — not something to chase during initial setup.

4. Set up Systems Manager (SSM) access

This is what lets you manage the server from any laptop without an open SSH port.

In AWS IAM, click Roles → Create role. On the first screen, choose AWS service as the trusted entity type, then select EC2 from the use-case list below it — this step is easy to miss, and skipping it means the role won't appear as an option when you try to attach it to your instance. Attach the AmazonSSMManagedInstanceCore policy, name the role, and create it. Then go to your EC2 instance → Actions → Security → Modify IAM Role, and attach it.

Once active, open a terminal right from your browser via Systems Manager → Session Manager → Start session. This logs you in as a different user than SSH does (ssm-user instead of bitnami), so the very first thing to run in every Session Manager tab is sudo su - bitnami — after that, commands behave exactly like the SSH terminal from Weekend 1. Then go back to the security group from Weekend 1 and delete the port 22 SSH rule entirely.

Weekend 3 · Moodle & the course 4–6 hrs

Goal: end this weekend with a branded, working course shell.

1. Secure the Moodle admin login

Log in using the credentials found in Weekend 1. Change the password immediately in Moodle, and turn on Moodle's built-in two-factor authentication (Site admin → Security → Multi-factor authentication) for the admin account.

2. Apply the ActiveSTEM theme

Moodle's default theme is called Boost, and its color settings live one level deeper than the main Appearance page: go to Site administration → Appearance → Themes → Boost, then look for a "Advanced settings" tab within it — that's where a "Brand colour" field or a "Raw initial SCSS" box lives, depending on your Moodle version. Set the brand colour to navy #1D2C48 directly if that field exists; if you only see the SCSS box, paste this instead:

$primary: #1D2C48; $secondary: #2C5545;
The exact field name shifts between Moodle versions more than almost anything else in this guide. If neither of the above is visible, search "Boost theme brand colour" plus your Moodle version number — this is the one step worth a quick web search rather than guessing.

3. Create the course shell

Site administration → Courses → Add a new course. Four fields are required and easy to trip on the first time:

Course full nameExtreme Algebra
Course short nameMust be unique site-wide — e.g. EA-2026-Pilot
Course categoryClick "Create new category" if none exists yet — e.g. "ActiveSTEM Online"
Course format"Topics format" — one section per unit fits the 12-session structure

Set Course visibility to "Hide" for now — you'll switch it to "Show" as the very last action in Weekend 5. No video anywhere in this course — text, LaTeX-rendered material, hints, and problems only.

4. Build the hint-based structure

Inside your course, click the "Turn editing on" toggle (top-right of the course page). Inside any topic section, click "+ Add an activity or resource" and choose Lesson.

Structure each Lesson as: a problem-statement page → the student attempts an answer → a wrong answer branches to a hint page → the student is routed back to try again. This is the fiddliest screen in Moodle for a first-timer — the branching is configured per-page via "Content page" question types with jump targets, not a single settings screen.

Give yourself extra time here specifically, and don't be surprised if the first Lesson takes 45–60 minutes even though later ones go faster once the pattern clicks. Moodle's own Lesson activity documentation is worth having open in a second tab the first time through — it covers the page-and-branch mechanics in more depth than fits here.

5. Install the certificate plugin

Under Site administration → Plugins → Install plugins, search for "Custom certificate" in the box that searches the official Moodle plugin directory directly — you don't need to download anything yourself. Click Install, confirm the version compatibility screen, and Moodle installs it in place. Then, inside your course, add it the same way as the Lesson activity ("Turn editing on" → "+ Add an activity or resource" → Custom certificate), and set its availability restriction to require a passing grade in the gradebook — not simply "course completed" or "activity viewed."

6. Verify Moodle's own cron is running

This is separate from the S3 backup cron in Weekend 5, and easy to miss. Moodle relies on its own internal scheduled task — not just the operating system — to send queued emails, issue certificates, and process gradebook updates. If it's not running, SES and the certificate plugin can be configured perfectly and nothing will still leave the queue, with no obvious error shown anywhere.

Bitnami images usually pre-configure this to run every minute, but "usually" is exactly why it's worth confirming.

In Moodle, go to Site administration → Server → Tasks → Task logs — you should see entries appearing roughly once a minute. If it looks stale, open a Session Manager terminal and check which user runs it, since Bitnami versions vary: try sudo crontab -l -u bitnami and, if that's empty, sudo crontab -l -u daemon. Confirm a line calling admin/cli/cron.php exists and runs every minute. If neither shows it, add it under whichever user your Moodle files belong to — typically: sudo crontab -e -u daemon, then add the line * * * * * php /bitnami/moodle/admin/cli/cron.php >/dev/null 2>&1, save, and check the Task logs page again a minute later.

7. Lock down course access

Nothing technical can stop a determined person from copying content off any web page they can see — that's true of every site, not just yours. What these settings do is close the specific holes that let someone bypass paying and enrolling in the first place, or take everything in one click instead of one page at a time.
Turn off self-registrationSite administration → Plugins → Authentication → Manage authentication. Confirm "Email-based self-registration" is disabled. Your enrollment flow is Stripe payment → manual add by you — self-registration left on would let anyone create an account and enroll themselves for free.
Turn off guest accessInside the course: Participants → Enrolment methods. Make sure "Guest access" is disabled — otherwise anyone with the course link can browse content without any account at all.
Disable "Download course content"This is the one worth knowing about: Moodle 4.x has a built-in button that lets any enrolled student export the entire course as a single file in one click. In course settings, set "Enable download course content" to Disabled — it's a much bigger leak than someone viewing one page's HTML.
Keep the course out of search resultsWith visibility set to "Hide" (Weekend 3, Step 3) this is already handled, but confirm it stays hidden until you're actually ready to enroll students — a search engine that indexes it once will keep showing it in results even after you hide it again.

End of weekend 3 checkpoint: walking through the course as a test student — wrong answer, see a hint, get it right, grade updates — Moodle's task log shows recent activity, and self-registration, guest access, and course download are all confirmed off.

Weekend 4 · Money & messages 3–5 hrs

Goal: end this weekend able to take a $50 payment and have Moodle send emails.

1. Create a Stripe Payment Link

Go to Stripe, create a product "Extreme Algebra — Online Pilot" for $50. Stripe hosts the checkout. Enrollment is manual: check Stripe, then enroll the student in Moodle yourself.

2. Set up outgoing email (Amazon SES)

Without this, password resets and certificate emails silently fail to send.

a. Verify domain: In the AWS console, go to SES → Verified Identities → Create Identity. Choose Domain, enter activestem.org. AWS generates three CNAME records.

b. Connect Cloudflare: Open your Cloudflare DNS dashboard and add those three CNAME records. This proves you own the domain.

c. Request production access: SES starts in a restricted "sandbox." Request production access in the SES dashboard — a short form, usually approved within a day.

d. Configure Moodle: Once approved, get your SMTP credentials from SES and enter them under Moodle's Site admin → Server → Email → Outgoing mail configuration.

3. Set up a support channel

Add a Moodle course forum for async questions. Post a standing Zoom link for optional office hours on the homepage.

4. Write the terms of service and privacy page

Cover: data collected, refund policy, and confirmation that a parent completes enrollment for minors.

Weekend 5 · Safety net & launch 3–5 hrs

Goal: end this weekend confident the system survives a failure.

1. Automate nightly backups to S3

You need to back up both the database and the moodledata folder to an S3 bucket.

a. Prepare AWS: Create an S3 bucket named activestem-backups-XXXX. In IAM, find the same role you created back in Weekend 2 for Systems Manager (don't create a second one) and attach the AmazonS3FullAccess policy to it alongside the SSM policy already there.

"Full access" is broader than this task actually needs — it can touch every S3 bucket in your account, not just this one. That's fine for a pilot and matches everything else in this guide favoring "get it running correctly" over premature tightening, but it's worth knowing it's not the tightest possible setup, and scoping it down to just this one bucket is a reasonable thing to do once you're past the pilot.

a½. Find your real database name, username, and password. Bitnami generates these automatically — don't guess them. In your terminal (as the bitnami user), run sudo cat /bitnami/moodle/config.php | grep -E 'dbname|dbuser|dbpass' and copy all three values shown — config.php is restricted to root, so the plain cat without sudo will fail with a permission error.

a¾. Confirm the AWS CLI is installed. Run aws --version. If you see a version number, skip ahead — the S3 upload commands below will work automatically using your instance's IAM role, with no separate login needed. If you see "command not found," install it first: sudo apt update && sudo apt install awscli -y.

b. Create the script: Run nano /home/bitnami/backup.sh — this opens a blank file in a simple text editor directly in your terminal. Paste this (replace the bucket name, database name, username, and password with the values you just found):

#!/bin/bash DATE=$(date +%Y-%m-%d) BUCKET="s3://YOUR_S3_BUCKET_NAME" # 1. Backup MySQL Database mysqldump -u YOUR_DB_USER -p'YOUR_DB_PASSWORD' YOUR_DB_NAME > /tmp/db_$DATE.sql # 2. Compress Moodle Data folder sudo tar -czf /tmp/data_$DATE.tar.gz /bitnami/moodle/moodledata # 3. Copy to AWS S3 aws s3 cp /tmp/db_$DATE.sql $BUCKET/ aws s3 cp /tmp/data_$DATE.tar.gz $BUCKET/ # 4. Clean up temp files rm /tmp/db_$DATE.sql /tmp/data_$DATE.tar.gz

After pasting, save and exit nano with Ctrl+O, then Enter, then Ctrl+X. Make the file executable: chmod +x /home/bitnami/backup.sh. Test it once by hand before automating: ./backup.sh — then check your S3 bucket in the AWS console for the two new files.

c. Automate it: This backup job is separate from Moodle's own internal cron in Weekend 3 — that one runs Moodle's PHP code as the bitnami user; this one is a system-level task, so it goes in root's crontab instead: run sudo crontab -e (the first time, it may ask which editor — choose nano), then add this line at the bottom to run it every night at 2:00 AM:

0 2 * * * /home/bitnami/backup.sh

Save and exit the same way (Ctrl+O, Enter, Ctrl+X).

2. Actually test a restore

A backup you've never restored from is an assumption, not a safety net. This is worth the full 45–60 minutes it takes — it's the one step that proves everything above it actually works.

a. Launch a second, temporary instance. Repeat Weekend 1, Steps 4 and 5 exactly — same Bitnami Moodle AMI, same t3.small, and the same security group rules (this second part matters — without it, SSH won't have anywhere to connect). Name it something obviously temporary, like activestem-restore-test, so you don't confuse it with your real server later.

b. Connect to it the same way as Weekend 1, Step 7 (SSH with the same or a new key pair — this instance doesn't have Session Manager set up, so SSH is the only option here, which is fine for a temporary test box).

c. Download last night's backup files from S3:

aws s3 cp s3://YOUR_S3_BUCKET_NAME/db_YYYY-MM-DD.sql /tmp/ aws s3 cp s3://YOUR_S3_BUCKET_NAME/data_YYYY-MM-DD.tar.gz /tmp/

(Replace the date with the actual filename shown in your S3 console.)

d. Restore the database. On this fresh instance, find its own auto-generated database credentials the same way you found your real one — sudo cat /bitnami/moodle/config.php | grep -E 'dbname|dbuser|dbpass' — then load your backup into it:

mysql -u YOUR_DB_USER -p'YOUR_DB_PASSWORD' YOUR_DB_NAME < /tmp/db_YYYY-MM-DD.sql

e. Restore the files. Extract your backed-up moodledata over the fresh instance's own folder:

sudo tar -xzf /tmp/data_YYYY-MM-DD.tar.gz -C /

f. Verify. Visit this temporary instance's own public IP in your browser, log in with your real admin credentials, and confirm the Extreme Algebra course, its content, and your test student's grades all appear exactly as they did on the real server.

g. Clean up. Once verified, terminate this temporary instance from the EC2 console — it's served its purpose and there's no reason to keep paying for it.

Write down how long the whole thing took you. That number is what goes in the runbook next.

3. Turn on uptime monitoring

Sign up at uptimerobot.com (free), point it at https://learn.activestem.org, and set it to email you if the site drops.

4. Write a one-page runbook

Document how to restore from S3, the monthly checklist, and emergency contacts.

5. End-to-end test, then launch

Walk through the entire flow as a stranger: pay via Stripe, get manually enrolled, hit a hint, submit, and receive the certificate via SES email.

Every term used anywhere in this guide, defined once.

EC2 instanceThe actual rented computer.

Web server (Apache)Software that receives requests and routes them to Moodle's code.

Download course contentMoodle 4.x's built-in one-click full-course export. Disable it per course — otherwise any enrolled student can take everything at once.

Security & compliance

Before taking any payment

  • MFA enabled on the AWS root account and your IAM admin user
  • SSH closed in the security group; Systems Manager used instead
  • SSL mode set to "Full" in Cloudflare, not "Flexible" or "Full (Strict)"
  • Terms of service and privacy policy page published
  • Parent/guardian completes enrollment for minor students
  • Outgoing email (SES) tested and working
  • Self-registration and guest access confirmed off; "Download course content" disabled

Before a second cohort or any institutional conversation

  • A real restore-from-backup has been performed and verified
  • Uptime monitoring is on and alerting you by email
  • A written one-page runbook exists
  • Moodle admin login has two-factor authentication turned on
  • Course content and gradebook are login-gated, not on the public marketing site
For a future DESE-type relationship: the certifications that matter live on AWS's side (SOC 2, ISO 27001), since that's where student data is processed. FERPA requires "reasonable safeguards," not a specific hosting certification — encryption at rest, restricted access, and tested backups are what you'd point to.

Routine maintenance

Running a server is not a "set it and forget it" task. Perform these steps once a month via an AWS Systems Manager terminal to keep the platform secure and stable.

1. Update the operating system

Just like your Mac, the server needs security patches. Run: sudo apt update && sudo apt upgrade -y

2. Check disk space

Run df -h. Look at the row ending with / (the root drive). If "Use%" is above 85%, clear old logs or increase your EBS volume size before the server fills up.

3. Check memory & swap usage

Run free -m. Confirms how much RAM Moodle is using and that your 2GB swap file (Weekend 1) is active and ready to catch spikes.

4. Verify S3 backups

Don't just trust the cron job. Open the S3 console and visually confirm a backup file with today's date exists.

Troubleshooting

  • The site won't load at all.

    Check Cloudflare DNS — does the A record match your EC2 Elastic IP? If you restarted the instance without an Elastic IP attached, the address changed.

  • SSH connection times out or is refused (Weekend 1 only, before SSM is set up).

    Your security group's port 22 rule only allows the IP address you had when you set it up. If you're connecting from a different network now (home vs. a coffee shop, a different day), your IP has likely changed. Go to the security group, edit the port 22 rule, and reselect "My IP" to refresh it. This entire class of problem disappears once Weekend 2's Session Manager is set up.

  • Can't open a Systems Manager terminal.

    Confirm the IAM role with AmazonSSMManagedInstanceCore is attached to the EC2 instance (Actions → Security → Modify IAM Role). It can take a few minutes to register after attaching.

  • Emails aren't sending.

    Confirm AWS approved your SES "Production Access" request — until then you're in the sandbox and can only send to addresses you've manually verified. If access is approved, also check Weekend 3's Moodle cron step — a stuck internal queue looks identical to an SES problem from the outside.

  • The nightly backup didn't run.

    Check the cron job's log output through a Session Manager session. Confirm the IAM role attached to the instance actually has the AmazonS3FullAccess policy.

  • A Moodle update seems risky to apply.

    Don't just take a manual database backup — go to the EC2 console, select the instance, and click Actions → Image and templates → Create image. This snapshots the entire server, not just the database, and if the update breaks something, you can launch a fresh instance from that image in about three minutes rather than reconstructing the server by hand.
